# Recovering a Hub turn after a writer exits

A tool result is not a completed turn. A completed, correctly attributed answer is not a committed ledger decision. Check the task thread, turn receipt, and scoped staging/ledger separately.

## Confirmed answer: host restart

1. A confirmed answer first gets a task-local write-ahead job in `tasks/<task-id>/archive-jobs/`. It contains the input needed to finish filing it. A new task's job can precede its index entry.
2. The writer publishes the user/assistant records together, then updates the index, the binding (only if its expected epoch still matches), and the receipt. A pre-existing single matching role from an older writer can be completed; contradictory content is not merged.
3. A fresh Hub host actively checks for these jobs. It finishes local writes, then schedules pending extraction outside the answering turn. A durable proposal is keyed by session, turn and ledger scope; recovery does not create a second proposal. If a worker exited before creating a proposal, its model call can run again. This is **not** exactly-once model billing.
4. Once extraction has a recorded outcome the job is removed. `staged` records what extraction produced, not whether a human subsequently committed or dropped it. `/cairn turns <turn>` reports the outcome in the originating session. `/cairn status` lists archive recovery issues found at startup. Preserve the store for diagnosis if a job is blocked; do not manually mark it complete.

This recovery replays **local Cairn bookkeeping only**. It does not run the original user request, rerun native tools, or reissue a write/deploy/send. An older Hub with a pending receipt but no write-ahead job may need the original completed turn to be redelivered. A crash before publication of any job likewise has no confirmed answer payload to recover from the Hub alone.

An independent read-only preview cannot clear locks. It can return `hub_snapshot_busy` after bounded retries, even when a writer has died. Start a host on the same machine and store: recovery acquires the writer lock and reaps the guard of a demonstrably dead local PID. Do not delete a live, foreign, or ambiguous owner's lock. The tests cover process exit, not filesystem corruption, machine power loss, network filesystems, or PID reuse.

## Interrupted turn: verify effects before doing more work

For an operator, `cairn tool-calls <task-id> --store <hub> --json` lists the task's **observed native call/result metadata** across sessions, including archived turns. Add a turn and session to narrow the read: `cairn tool-calls 1 7 --session dsh-session-id --store <hub> --json`. The query is read-only and never executes tools. The full timeline is not mounted into a model prompt.

* `result_status: "unknown"` means Cairn saw the native call but has no reliably matched result. The tool may have run, partially run, or never started. Do not retry a side effect on this evidence alone.
* `result_status: "observed"` identifies native result sequences and their reported `ok` flags. Neither the flag nor a receipt verifies external effects. Unmatched results remain separate; missing or ambiguous call IDs do not justify guessing a link.
* Task-local `tool-timeline/` pages retain identifiers, names, steps, sequences and statuses, **not arguments or output**. This is distinct from the bounded, masked result excerpts in `observations/`, and from the independently verifiable file-write intents. Metadata survives excerpt eviction and successful turn archival. It starts with this version: an empty list does not certify that no tool ever ran. Events lost before publication or without a demonstrable active binding cannot be recovered from this index.

- A checkpoint requires an already bound active task, a matching binding epoch, and an appended native tool result with a journal sequence. A missing checkpoint does not mean a tool had no effects: the process may have died after an external write but before its result was delivered. Provisional task selection is not durable attribution.
- Use the task's read-only checkout preview and inspect `work_state.pending_turns`, including `source.session_id`, `source.turn`, the step and journal sequence, tool names, success flags, and output excerpts. New observations and archived tool evidence carry the native `call_id` when available; Cairn does not invent one if the native ID is absent. Multiple tools in one step have distinct journal sequences. A success flag or an old output excerpt does not establish the current state of an external system.
- Each outstanding turn retains the first and most recent 31 results when there are more than 32. `omitted_tools` counts the missing results. For new checkpoints `omitted_journal_seq` brackets the omitted results (other native events can fall inside the interval). Older checkpoints may lack an interval or have only `last_tool`; upgrading cannot recreate missing events. The handoff view also limits the number of outstanding turns and reports the full count.
- **32 excerpts cannot prove a complete sequence of side effects.** For older results use `tool-calls` to inspect the retained metadata; for omitted output use the originating native session journal with the session, turn and sequence range. Check independent evidence such as current file bytes or the external service's read-only operation record before retrying a side effect. If the native journal is gone or the evidence is insufficient, report the effect as unknown and ask the operator; do not infer that a missed operation failed. An `in_progress` receipt is not a process-liveness signal.

## Sensitive data and retention

Session receipts link status and provenance; checkpoint request/output excerpts are stored under the task's `observations/`, **not** in the receipt. A request excerpt is capped at 320 characters, a tool name at 128 and a result excerpt at 500 (JavaScript string units). These are size limits, not a privacy guarantee.

New dsh tool **output text** is masked before selecting high-signal lines or truncating: Basic/Bearer authorization headers, explicitly assigned credential fields such as `API_KEY`, `clientSecret`, `ACCESS_TOKEN` or `password`, and PEM private-key blocks become `<redacted>` values. Cairn does not inspect or copy native screenshot/image blocks into these tool excerpts. Ordinary measurements, file hashes and status codes are not masked by value or length alone. The filter does not edit the native journal or recalculate file verification hashes.

This is a narrow safeguard, not a secret scanner. Unlabeled secrets, free-form prose, screenshot captions, encoded data, user requests, assistant answers and ordinary identifiers can still contain private data. No migration rewrites or certifies older evidence, pending jobs, previews or backups. Copied historical excerpts may be unmasked. If you need assurance that a string never leaves the source, remove it at the producing tool before dsh receives it.

Treat the store, backups, checkout JSON and the original dsh journal as private. Archived task threads and pending archive jobs can also contain answer text and tool excerpts. Handoff can present task evidence to the selected model; a local-first store does not imply local-only inference. Do not share raw previews as diagnostics. Share the task/turn identifier, receipt outcome, tool name and sequence first; redact sensitive excerpts before sharing them. Removing an archived job or its observation does not erase a separately retained backup, native journal or an already filed thread.
